# Landing page and join-logic refactor

The minimal "You're not in a meeting yet!" placeholder is replaced with a dedicated `LandingPage` component offering a hero section, a "Start Meeting" button (generates a random PIN), a "Join Meeting" form, and feature highlight badges. The join logic previously embedded in `MeetingControlBar` is lifted into `App.tsx` (now split into an outer `App` shell providing Chime context and an inner `MeetingApp` that owns state). `MeetingControlBar` is simplified to an in-meeting-only control bar that returns `null` when no session is active. URL-based auto-join (reading the path to pre-fill a meeting PIN) remains but now lives in `MeetingApp`'s `useEffect`.

**Watch for:** unhandled promise rejection on auto-join failure (confirmed), `isLoading` shared across both buttons creating ambiguous disabled state (confirmed), and `Math.random()` PIN generation yielding short/predictable meeting names (likely).

## High-level view

The component hierarchy splits into `App` (context providers), `MeetingApp` (join lifecycle and state), and `LandingPage`/video components (presentation). The join logic moved verbatim from `MeetingControlBar` to `MeetingApp`, gaining a `try/finally` wrapper — but still lacking a `catch`, so failures during auto-join produce no user-visible feedback.

`LandingPage` delegates join work to its parent via `onJoinMeeting` and `await`s it inline. Because there's no error boundary or catch at the call site inside `LandingPage`, a failed join resets loading state but never tells the user what went wrong.

`MeetingControlBar` now gates rendering on `useAudioVideo()` truthiness and returns `null` when no session exists, eliminating the conditional pre-meeting UI that cluttered it before.

<summary>Issues (4)</summary>

1. **Auto-join fires without error feedback** — the `useEffect` calls `handleJoinMeeting` without catching rejections; a failed auto-join shows a flash of loading state then silently returns the user to the landing page. Add a `.catch()` that sets an error message visible on the landing page.
2. **Shared `isLoading` disables both action paths** — a single boolean gates "Start Meeting" and "Join Meeting" buttons; if auto-join triggers on mount, both buttons show spinners simultaneously. Consider tracking which action is in progress or passing the loading source.
3. **Short/predictable meeting PINs** — `Math.random().toString(36).substring(2, 8)` produces ~6 alphanumeric characters (~31 bits of entropy). Depending on whether meeting PINs are meant to be unguessable, this may be too short. If meetings are meant to be semi-private, use `crypto.getRandomValues` or a longer slug.
4. **Missing `useCallback`/dependency for `handleJoinMeeting`** — the function is referenced in a `useEffect` with an empty dependency array; ESLint's `exhaustive-deps` rule will flag this. Wrapping in `useCallback` or moving the logic inside the effect avoids a stale-closure risk.

## Error handling gap on auto-join

The `useEffect` in `MeetingApp` calls `handleJoinMeeting(path)` as a fire-and-forget async invocation:

```tsx
useEffect(() => {
  // ...trim path...
  if (path.length) {
    handleJoinMeeting(path);
  }
}, []);
```

`handleJoinMeeting` uses `try/finally` (no `catch`), so if `getMeetingMetadata` returns an error or the network request fails, the promise rejects without any user-facing feedback. The `finally` block resets `isLoading`, so the landing page reappears, but the user sees no indication that an auto-join was attempted and failed. Adding a `catch` that sets an error state string — passed to `LandingPage` for display — would close this gap. The same issue applies to the `onJoinMeeting` calls inside `LandingPage` (`handleStartNewMeeting` and `handleJoinMeeting` both `await` without catching). Confidence: **confirmed**.

## Shared loading state ambiguity

A single `isLoading` boolean in `MeetingApp` is threaded into `LandingPage` and used by both buttons. When auto-join fires on mount, both buttons render with spinners simultaneously — confusing because neither was user-initiated. During a normal flow, clicking "Start Meeting" also shows the "Join Meeting" button as loading. A more precise approach: track `loadingAction: "start" | "join" | "auto" | null` and only show the spinner on the relevant button. Confidence: **confirmed**.

## Meeting PIN entropy

`handleStartNewMeeting` generates a PIN via `Math.random().toString(36).substring(2, 8)`. This produces a 6-character base-36 string (~31 bits). If meetings should be non-enumerable (hard to stumble into by guessing), 6 characters is brute-forceable. The prior code required users to type their own PIN, so this is a new behavior introduced by the landing page. Using `crypto.getRandomValues` with a longer output (8-10 chars) would make random collisions and guessing significantly harder at no UX cost. Confidence: **likely** (depends on product requirements for meeting privacy).

## Stale closure in useEffect

`handleJoinMeeting` is defined as a regular function inside the component body and referenced inside a `useEffect` with `[]` deps. React's `exhaustive-deps` lint rule will flag this. If `MeetingApp` ever re-renders before the effect fires (e.g., due to a parent state change), the closure could capture stale state. Wrapping `handleJoinMeeting` in `useCallback` with appropriate deps, or inlining the auto-join logic inside the effect, would satisfy the lint rule and prevent future issues. Confidence: **confirmed** (lint violation is mechanically certain; runtime impact is theoretical but the pattern is fragile).
